At a glance

Larkspur is a team-wiki SaaS: shared pages, comments, and role-based access. The codebase is small and well organized, with real authentication and a clean data layer. Two things need attention before it carries paying teams: a page-permission check that runs only in the browser, and thin automated test coverage. Neither is alarming at this size, and both are quick to address.

What the system does

Larkspur is a standard web app: a React front end, a small API, and a database. Pages and comments are stored in the database; what a member can do is decided by their role in each workspace.

CapabilityIn plain terms
Pages & editingCreate, edit, and organize wiki pages with version history.
CommentsThreaded comments on any page, with mentions and resolve/reopen.
Workspace & rolesTeam workspaces with Editor and Admin roles; admins manage members and settings.

Top things to know

High · security

A page-permission check runs only in the browser

What this means for you: a member could reach or edit a page they shouldn't by calling the API directly, because the permission check happens in the interface rather than on the server. Low impact today, but it undermines the role system paying teams will rely on. About a day to fix.
Medium · quality

Tests cover the happy paths only

What this means for you: edge cases like permission failures and simultaneous edits can break without any test catching them, which slows safe iteration as the team grows.

What we recommend

Quick wins

  • Add the server-side page-permission check. Closes the one real access-control gap; about a day of work.

Strategic

  • Grow the test suite around authorization and simultaneous edits. Protects the riskiest logic as the product scales.

Questions worth asking your developers

  • "Can a member reach a page through the API that the interface would hide from them? When can we add the server-side check?"
  • "Which parts of the code have no tests today, and which would you cover first?"
